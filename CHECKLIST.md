# Checklist de desarrollo — Sistema de Gestión Escolar

Stack: Laravel 11 (PHP 8.3+) + Inertia.js + Vue 3 + Tailwind CSS + MySQL/MariaDB.
Referencia funcional completa: [plan.md](plan.md).

Marcar `[x]` al completar. Cada fase corresponde a uno o más módulos del plan (sección 44) y debe dejar migraciones + modelos + páginas Vue + pruebas básicas funcionando antes de pasar a la siguiente.

## Fase 6 — Asistencia (Módulo 8)
- [x] Migraciones `attendances` (tabla `attendance` del plan, en plural por convención de Eloquent) y `attendance_corrections`
- [x] Registro de asistencia vinculado a una clase (`class_session_id`) y a una matrícula (`enrollment_id`, de donde se deriva el estudiante) — captura además `teacher_id`, `class_date`, `registered_by_id` y `created_at` como "hora de registro" con hora del servidor
- [x] Restricción única `(class_session_id, enrollment_id)`: no se puede registrar dos veces la asistencia de un estudiante en la misma clase
- [x] Inmutabilidad real, no solo de UI: `AttendanceController` **no tiene** rutas `update`/`destroy` (verificado con `route:list`); la única forma de ajustar una asistencia es `AttendanceCorrectionController@store`, que crea un registro nuevo en `attendance_corrections` sin tocar el original — ni siquiera el rol admin puede saltarse esto, porque la capacidad de editar/borrar simplemente no existe en ninguna ruta
- [x] Estado "efectivo" (`Attendance::effective_status`): la última corrección si existe, si no el estado original — así el resto del sistema (horas, reportes) siempre lee el valor correcto sin perder el histórico
- [x] Cálculo de horas: `App\Actions\Attendance\RecalculateEnrollmentHours` recalcula `accumulated_hours` **desde cero** (no incrementa/decrementa) sumando la duración de cada clase con asistencia efectiva "presente"; se ejecuta tras cada registro y tras cada corrección — así una corrección retroactiva siempre deja las horas consistentes
- [x] Decisión: solo "presente" acumula horas; "excusado" tampoco acumula (igual que "ausente"), interpretando "asistencias válidas" de la sección 17 de forma estricta — si se prefiere que "excusado" sí sume horas, es un cambio de una línea en la Action
- [x] `accumulated_hours` de `Enrollment` ya no es editable manualmente desde el formulario de matrícula (se quitó el input de las Fases 5); ahora es de solo lectura, alimentado exclusivamente por este módulo
- [x] UI: "Tomar asistencia" por clase (roster de matriculados activos en el nivel, con los ya registrados bloqueados) desde el calendario; listado "Asistencias" con filtros (fecha/estudiante/nivel) y modal de corrección auditada
- [x] Validado en Tinker reproduciendo el ejemplo exacto de la sección 17 del plan: 3 clases "presente" + 1 "ausente" de 2 horas cada una → 6 horas acumuladas, 122 pendientes; corregir la "ausente" a "presente" → sube a 8 horas, y la columna `status` original permanece "ausente" para siempre. También confirmé: profesor solo puede tomar asistencia de sus propias clases, y el índice único bloquea el doble registro

## Fase 7 — Evaluaciones (Módulo 9)
- [x] Migraciones `evaluations` y `evaluation_results` — se simplificó a 2 tablas en vez de las 3 del plan (`evaluations`, `evaluation_attempts`, `evaluation_results`): `evaluation_results` incluye `attempt_number` e `is_recovery`, así que un intento y su resultado son el mismo registro. Esto también absorbe lo que la Fase 8 necesita para las recuperaciones (no habrá una tabla `recovery_attempts` separada; una recuperación es simplemente un intento con `attempt_number` > 1)
- [x] Configuración de evaluaciones por nivel (nombre, competencia, nota mínima propia — puede diferir de la nota mínima general del nivel) — CRUD completo en `evaluations.*`
- [x] Validación de requisitos para presentar evaluación (`App\Actions\Evaluations\CheckEvaluationEligibility`): horas completas, matrícula en estado activo/en_recuperacion/extendida, nivel vigente — bloquea el registro con el mensaje "NO APTO PARA PRESENTAR" + lista de lo que falta, igual que el ejemplo de la sección 20 del plan. El requisito genérico "cualquier otro requisito configurado" no se implementó (no hay UI para reglas configurables) — documentado como simplificación
- [x] Lógica de aprobación de nivel (`App\Actions\Evaluations\EvaluateLevelCompletion`): tras cada resultado, si TODAS las evaluaciones activas del nivel tienen su intento más reciente en "aprobado" y las horas están completas → matrícula pasa a `aprobada` (con `actual_end_date`); si alguna sigue en "reprobado" → pasa a `en_recuperacion`. Usa siempre el **intento más reciente** por evaluación, así que una recuperación aprobada revierte el estado a `aprobada` automáticamente
- [x] Igual que evaluaciones/asistencia: sin rutas `update`/`destroy` para `EvaluationResult` (Regla 4 del plan — un resultado confirmado no se modifica; una corrección es un nuevo intento, nunca una edición)
- [x] Validado en Tinker reproduciendo los ejemplos exactos de las secciones 20 y 21 del plan: con 100/128 horas → "Faltan: 28 horas académicas"; con 128/128 horas y notas 85/78/91/88 en las 4 competencias → matrícula `aprobada`. Caso de recuperación: reprobar Speaking (55) → `en_recuperacion`; segundo intento con 75 → vuelve a `aprobada` automáticamente. También confirmé que no se puede duplicar un `attempt_number` para la misma evaluación/matrícula

- [x] Migraciones: `recovery_settings` (config global, fila única) y `extensions`

- [x] Continuidad de clases durante recuperación (sección 26): ya estaba cubierta desde la Fase 6 — el roster de asistencia ya incluye matrículas en estado `en_recuperacion`
- [x] Validado en Tinker reproduciendo el ejemplo **exacto** de la sección 23 del plan: Intento #1 (55, reprobado, $0) → Recuperación #1 (62, reprobado, $0) → Recuperación #2 (65, reprobado, $50.000) → Recuperación #3 (72, aprobado, $50.000) → total pagado $100.000, y la matrícula pasa a `aprobada` automáticamente. También confirmé el bloqueo al superar el máximo de recuperaciones, el cálculo de fecha límite (último intento + 15 días) y el registro de una extensión de nivel

## Fase 10 — Auditoría (Módulo 14)
- [x] Migración `audit_logs` (usuario + rol *snapshot* como texto plano, no solo FK — así el registro sigue siendo legible aunque el usuario cambie de rol o se elimine después; acción, módulo, tipo/id polimórfico del registro afectado, descripción, `old_values`/`new_values` en JSON, IP, y solo `created_at` — es un registro de solo escritura, sin `updated_at`)
- [x] **`App\Observers\AuditObserver`** en vez de Events + Listeners por operación: un único observer registrado sobre los 10 modelos críticos de la sección 38 (Attendance, AttendanceCorrection, EvaluationResult, Payment, Extension, Enrollment, Promotion, Referral, ClassSession, ClassSchedule) en `AppServiceProvider::boot()`. Registra automáticamente `created`/`updated`/`deleted`, capturando solo los campos que realmente cambiaron (no todo el registro) en las actualizaciones. Se prefirió a Events+Listeners porque son funcionalmente equivalentes para este caso pero con muchísimo menos código repetido — no hace falta una clase de evento por cada acción de cada módulo
- [x] Vista de consulta de auditoría (`audit-logs.index`) con filtros por fecha, módulo, usuario y acción, y un panel expandible para ver el diff antes/después de cada registro
- [x] Validado en Tinker: crear/editar una matrícula (modelo observado) genera su registro de auditoría con usuario, rol y módulo correctos, y el diff de la actualización contiene *solo* el campo que cambió; crear/editar un curso (modelo **no** observado, fuera de la lista de la sección 38) no genera ningún registro — confirmando que el observer no audita todo el sistema, solo lo crítico
